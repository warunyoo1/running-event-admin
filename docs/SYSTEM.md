# ระบบหลังบ้านรับสมัครงานวิ่ง (Running Event Admin)

สถานะเอกสาร: เริ่มพัฒนา Frontend สาธิตแล้ว (15 ต.ค. 2569) ยังไม่เชื่อมต่อ Backend
Repo นี้: Frontend (Next.js) ของระบบ Admin เท่านั้น

### สถานะ Frontend ปัจจุบัน
- Next.js App Router + TypeScript (strict), CSS ส่วนกลาง, Lucide และ Noto Sans Thai ที่โหลดจากแพ็กเกจในโปรเจกต์
- โค้ดอยู่ใน `src/app` แยก route ตามโมดูล, `src/components` สำหรับ UI ร่วม และ `src/features/admin` สำหรับชนิดข้อมูลและ state สาธิต
- มีหน้าภาพรวม งานวิ่ง ออเดอร์ ตรวจสลิป ผู้สมัคร รับอุปกรณ์/จัดส่ง รายงาน และผู้ใช้
- เลือกงานที่ sidebar เพื่อกรองภาพรวม ออเดอร์ สลิป ผู้สมัคร การจัดส่ง และรายงาน โดยจำงานที่เลือกไว้ในเบราว์เซอร์; เมนูส่วนกลาง “จัดการงานวิ่ง” และ “ผู้ใช้และสิทธิ์” ไม่ถูกกรองตามงาน
- ใช้ข้อมูลสมมติ บันทึกการเปลี่ยนแปลงใน localStorage เท่านั้น ไม่มีระบบยืนยันตัวตน ตรวจสิทธิ์ หรือธุรกรรมจริง
- เริ่มพัฒนา: `npm install` แล้ว `npm run dev`; ตรวจสอบ: `npm run typecheck` และ `npm run build`
- ใช้ skill `ui-ux-pro-max` ร่วมกับ `frontend-design`; ยังไม่เพิ่มชุด UI, ตาราง หรือฟอร์มที่ไม่จำเป็นกับโครงปัจจุบัน

## 1. ที่มาและขอบเขต

อ้างอิงจากการวิเคราะห์เว็บ https://runrace.in.th/ (รายงานดิบ: `.agents/tasks/runrace-ui-analysis.md`)
เว็บต้นแบบเป็นแพลตฟอร์มรับสมัครงานวิ่งหลายผู้จัด ระบบนี้คือส่วน **หลังบ้าน (Admin)** ที่ใช้จัดการงาน ผู้สมัคร และการชำระเงิน

ข้อจำกัดของการวิเคราะห์: ไม่ได้ล็อกอินดูหน้า admin จริงของเว็บต้นแบบ โมดูลหลังบ้านจึงอนุมานจากหน้าบ้านและชื่อ route ไม่ใช่การเห็นหน้าจอจริง

### การตัดสินใจที่ตกลงแล้ว
| หัวข้อ | ข้อตกลง |
|---|---|
| Frontend | Next.js |
| การชำระเงิน | ใช้รูป QR ที่มีอยู่แล้ว (ไม่ผ่าน payment gateway) ผู้สมัครอัปโหลดสลิป แอดมินตรวจเอง |
| Backend | ยังไม่กำหนด (ดูข้อ 9) |

### ค่าเริ่มต้นที่เสนอ (รอยืนยัน)
- Next.js App Router + TypeScript
- Tailwind CSS + shadcn/ui
- TanStack Table (ตาราง), React Hook Form + Zod (ฟอร์ม), TanStack Query (เรียก API)
- Session เก็บใน cookie แบบ httpOnly ตรวจสิทธิ์ที่ backend

## 2. ผู้ใช้และสิทธิ์

| บทบาท | ทำอะไรได้ |
|---|---|
| Super Admin | ทุกอย่าง ทุกงาน รวมถึงจัดการผู้ใช้ |
| เจ้าหน้าที่ตรวจสลิป | ดูออเดอร์ ตรวจสลิป อนุมัติ/ปฏิเสธ |
| ผู้ดูข้อมูล (Viewer) | ดูและ export อย่างเดียว ห้ามแก้ |

หมายเหตุ: ถ้าอนาคตมีผู้จัดหลายราย (multi-organizer) ให้เพิ่มบทบาท Organizer ที่เห็นเฉพาะงานของตัวเอง ควรออกแบบข้อมูลให้ผูกงานกับผู้จัดตั้งแต่ต้น

## 3. โมดูล MVP

### 3.1 ล็อกอินและผู้ใช้
- ล็อกอินด้วยอีเมลและรหัสผ่าน, ออกจากระบบ, เปลี่ยนรหัสผ่าน
- หน้าจัดการผู้ใช้และบทบาท (Super Admin เท่านั้น)

### 3.2 จัดการงานวิ่ง (Events)
- ข้อมูลงาน: ชื่อ, slug (ไม่ซ้ำ), วันที่จัด, สถานที่, รายละเอียด (rich text), รูปโปสเตอร์
- สถานะ: draft / open / closed, วันเปิด-ปิดรับสมัคร
- รูป QR รับเงินของงาน
- ข้อมูลผู้จัดและช่องทางติดต่อ, เงื่อนไขคืนเงินของงาน

### 3.3 ระยะ ราคา และไซซ์เสื้อ
- ระยะ (Race): ชื่อ, ราคา, ของที่ได้ (เสื้อ/บิบ/เหรียญ), เวลาปล่อยตัว, โควตา
- ไซซ์เสื้อ: ชื่อไซซ์, รอบอก, ความยาว, จำนวนจำกัด
- แสดงยอดคงเหลือของแต่ละระยะและไซซ์

### 3.4 ออเดอร์และผู้สมัคร
- ตารางออเดอร์: ค้นหา/กรองตามงาน สถานะ เบอร์โทร ชื่อ
- หน้ารายละเอียดออเดอร์ (1 ออเดอร์มีผู้สมัครได้หลายคน, เว็บต้นแบบจำกัด 20 คน)
- แก้ไขข้อมูล เปลี่ยนระยะ เปลี่ยนไซซ์ ยกเลิกออเดอร์
- หน้ารายชื่อผู้สมัครแยกตามงาน

### 3.5 ตรวจสลิปชำระเงิน
- คิวสลิปที่รอตรวจ เรียงตามเวลา กรองตามงาน
- แสดงรูปสลิปคู่กับยอดที่ต้องจ่าย
- อนุมัติ/ปฏิเสธ พร้อมเหตุผล และอนุมัติหลายรายการพร้อมกัน
- เก็บเลขอ้างอิงธุรกรรมเพื่อกันสลิปซ้ำ
- ออเดอร์ที่ไม่จ่ายภายในเวลากำหนดหมดอายุและคืนโควตา
- บันทึกว่าใครตรวจเมื่อไร

### 3.6 รายงานและ Export
- Export รายชื่อผู้สมัคร (Excel/CSV) ต่องาน
- สรุปจำนวนเสื้อแต่ละไซซ์
- สรุปยอดสมัคร ยอดรับเงิน ยอดค้างตรวจ
- Dashboard ภาพรวมต่องาน

### 3.7 การรับอุปกรณ์และจัดส่ง
- แยกผู้ที่รับเองกับจัดส่ง, export รายการที่อยู่, ใส่เลขพัสดุ
- ติ๊กสถานะรับเสื้อและบิบแล้ว

## 5. ข้อมูลหลัก (ข้อเสนอ ไม่ใช่ schema จริงของเว็บต้นแบบ)

- **User**: id, email, password_hash, role, status
- **Organizer** (ถ้าทำหลายผู้จัด): id, ชื่อ, ช่องทางติดต่อ
- **Event**: id, organizer_id, slug, ชื่อ, วันที่, สถานที่, รายละเอียด, สถานะ, เปิด/ปิดรับ, รูป QR, เงื่อนไขคืนเงิน
- **Race**: id, event_id, ชื่อ, ราคา, ของที่ได้, เวลาปล่อยตัว, โควตา
- **ShirtSize**: id, event_id, ชื่อไซซ์, รอบอก, ความยาว, โควตา
- **Order**: id, order_no, event_id, ผู้ติดต่อ, วิธีรับของ, ที่อยู่จัดส่ง, ค่าจัดส่ง, ยอดรวม, สถานะ, หมดอายุเมื่อ
- **Participant**: id, order_id, race_id, shirt_size_id, ข้อมูลส่วนตัว, หมู่เลือด, ปัญหาสุขภาพ, ผู้ติดต่อฉุกเฉิน, ทีม, bib_no, รับของแล้วหรือไม่
- **Payment**: id, order_id, รูปสลิป, ยอด, เลขอ้างอิงธุรกรรม, สถานะ, ผู้ตรวจ, เวลาตรวจ, เหตุผลที่ปฏิเสธ
- **Shipment**: order_id, ผู้ให้บริการ, เลขพัสดุ, สถานะ
- **AuditLog**: user_id, action, เป้าหมาย, เวลา

### ฟิลด์ผู้สมัครที่เว็บต้นแบบเก็บ (เป็นแนวทางสำหรับฟอร์ม)
ชื่อ, นามสกุล, เพศ, วันเกิด, สัญชาติ, เลขบัตร/พาสปอร์ต (มีตัวเลือกไม่แสดงข้อมูล), อีเมล, เบอร์โทร, ปัญหาสุขภาพ/แพ้ยา/แพ้อาหาร, หมู่เลือด, ผู้ติดต่อฉุกเฉิน (ชื่อ/ความสัมพันธ์/เบอร์), ระยะ, ไซซ์เสื้อ, จังหวัด, ชื่อทีม

## 6. ข้อควรระวังเรื่องการจ่ายด้วย QR รูปคงที่

- QR เดียวกันทุกออเดอร์ทำให้จับคู่สลิปกับออเดอร์ยาก แนวทาง: บวกเศษสตางค์เฉพาะออเดอร์ (เช่น 399.17) หรือให้ผู้สมัครกรอกเลขออเดอร์ในสลิป
- ป้องกันสลิปซ้ำด้วยเลขอ้างอิงธุรกรรม
- ช่วงเปิดรับสมัครแอดมินต้องตรวจสลิปมาก ต้องมีหน้าตรวจแบบคิวและอนุมัติทีละหลายรายการ
- ตรวจสลิปอัตโนมัติผ่านบริการภายนอกเป็นทางเลือกในอนาคต (ยังไม่ได้ประเมินราคาและเงื่อนไข)
- คืนเงิน: โอนคืนเองแล้วบันทึกสถานะในระบบ

## 7. ความปลอดภัยและ PDPA

- เลขบัตร ข้อมูลสุขภาพ และสลิป เป็นข้อมูลอ่อนไหว จำกัดสิทธิ์ดู
- เก็บสลิปในที่เก็บไฟล์ที่ไม่เปิดสาธารณะ
- ปิดบังเลขบัตรในตารางและหน้าค้นหา แสดงเต็มเฉพาะผู้ที่มีสิทธิ์
- Audit log อย่างน้อยกับการอนุมัติสลิปและการแก้ข้อมูล
- ช่องทางรับคำขอแก้ไข/ลบข้อมูลตาม PDPA

## 9. คำถามที่ยังไม่มีคำตอบ

1. Backend ใครทำและใช้อะไร (REST? มี OpenAPI ไหม) ถ้ายังไม่มี ฝั่ง front ใช้ mock data ก่อนได้
2. QR รับเงินเป็นบัญชีเดียวทุกงาน หรือแยกตามงาน/ผู้จัด
3. ใครเป็นคนตรวจสลิป (ทีมกลาง หรือผู้จัดแต่ละงาน) กระทบการแยกสิทธิ์ผู้จัด
4. ต้องรองรับหลายผู้จัดตั้งแต่เริ่มหรือไม่
5. ต้องการสมัครหน้างาน, งานฟรี, ผลการแข่งขัน หรือไม่ (เว็บต้นแบบมีสมัครหน้างานและงานฟรี แต่ไม่พบผลการแข่งขัน)
6. ต้องการหน้าบ้านสำหรับผู้สมัคร (สมัคร/อัปโหลดสลิป) ใน repo นี้ด้วยหรือไม่ ตอนนี้เอกสารนี้ครอบคลุมเฉพาะ Admin
7. Skill สำหรับ admin panel: ติดตั้ง `ui-ux-pro-max` แล้ว และนำมาใช้วาง Frontend สาธิต (ดูสถานะ Frontend ด้านบน)
